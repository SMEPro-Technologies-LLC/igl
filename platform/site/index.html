Quickstart

Connect the igl_identity_mcp server with an API key and tenant id from the Developer Console (the same headers the REST contract uses), then call whoami before any task that depends on knowing the person. The answer is one their organization has governed, so it saves asking.

# mcp.json
{ "mcpServers": { "igl_identity_mcp": {
    "url": "https://api.id-me.ai/v1/mcp",   # self-hosted: http://127.0.0.1:8787/mcp from npm run provision
    "headers": { "X-IGL-API-Key": "igl_live_…",
                 "X-IGL-Tenant-Id": "e7bcde63-4ccd-4594-aa64-6de1cce72ae8" } } } }

# first call
whoami({ purpose: "identity-introduction" })

    employer: "Rio Diablo Operating", jurisdiction: "US-TX",
    truncated: false }

What you get is a projection, not the graph

The context you receive is deliberately partial. Every node is admitted through four gates in order: node type, sensitivity, consent, jurisdiction. The first failure is the reason a node is missing.

Absence of a fact is not evidence the fact is false. If someone asks about something the projection does not contain, say you do not have it in this context, not that it does not exist.

Proposed relationships are excluded. Anything not attested by a human never reaches the model, and that is correct behaviour, not a gap to work around.

Purposes

Ask for the purpose that matches the task, not the widest one available. You get less context, which is the point. list_purposes returns what each permits; read it rather than guessing from the name.

PurposeAdmitsTypical use
identity-introductionName, role, employer, jurisdictionThe default. Greeting, routing, addressing the person correctly.
directory-lookupName and title onlyRosters, mentions, org charts.
scientific-researchAdds credentials, occupational codes, facilitiesQualification checks, study eligibility.
regulatory-filingAdds obligations and the facilities that trigger themDeadline tracking, filing preparation.

Four things that change what you should say

  • truncated: true, the node budget bound before traversal finished. Say the context is incomplete rather than reasoning confidently over it.
  • empty_warning, no nodes admitted at all. The identity exists; the context does not. Usually no consent covers this purpose.
  • Proposed relationships are excluded. You will not see them. Do not work around it.
  • Obligation status. attested means a human reviewed it and it is a real deadline. proposed means the system computed it and nobody has checked. Never present a proposed obligation as a confirmed date.

Explaining a projection

When someone asks "how do you know that?" or "why don't you know that?", call explain_projection. Pass the reason through rather than paraphrasing it. "Your purpose profile does not permit Credential nodes" is actionable; "I don't have access" is not.

explain_projection({ purpose: "identity-introduction" })
 to  { "node": "Obligation:Q3-W3-filing",
    "gates": { nodeType: pass, sensitivity: pass,
               consent: fail, jurisdiction: ,  },
    "reason": "purpose profile does not permit Obligation nodes" }

Recording what you did

After doing something consequential on the person's behalf, call record_interaction, especially when you refused, or when the projection was incomplete and you proceeded anyway. It writes metadata only; the conversation is not captured.

record_interaction({
  purpose: "identity-introduction",
  outcome: "refused",
  reason: "obligation status was proposed, not attested",
  truncated: false })

What the server cannot do

It cannot change anything about governance. No profile edits, no consent grants, no attestation. That is the control plane's job, and the separation is deliberate: a model that can rewrite the policy governing it is not governed.

If a projection is too narrow for a legitimate task, tell the person which purpose or consent is missing so a human can widen it. Not find another route to the data.

API reference OpenAPI 3.1, v0.2.0

What changed in v0.2. The MCP governance model is now in the REST contract. A new Projection service adds purpose profiles (GET /purposes), caller resolution (GET /identities/me), purpose-bounded projections with node budgets and a per-node gate explanation, obligations carrying attested or proposed status, read-only consent records, and interaction records (POST /audit/interactions). Every intelligence request accepts a purpose. The 34 v0.1 paths are unchanged.

Proposed API contract for Identity Governed Logic (IGL). The API exposes governed identity, authority, knowledge, policy, evidence, outcome, graph, query, research, agent, workflow, and audit services. It is model-agnostic: reasoning providers can be changed without changing the governed intelligence contract. Version 0.2 adds purpose-bounded projections: purpose profiles, identity projections with per-node gate explanations, obligations with attestation status, caller resolution, consent records, and interaction records, so applications and model callers share one governance model.

The contract covers 42 paths, 46 operations, 63 reusable schemas and 3 webhooks. The source of truth is the specification file in the repository, spec/openapi.yaml, also served here as igl-openapi-v0.2.yaml (v0.1 kept for comparison).

Errors use application/problem+json (RFC 9457): type, title, status, traceId and optional field-level violations. 403 means the action was denied by authority or policy; 422 means the request was valid but could not be governed or executed; 429 carries Retry-After.         Separated control plane

        Purpose profiles, consent grants and attestation live in a control plane the model cannot reach. The MCP server can read a projection and record what was done with it. It cannot widen its own access.

        Cross-border by policy

        A transfer policy per jurisdiction gates every node before it crosses a border. A projection served in Texas and one served in Frankfurt differ by policy, not by configuration drift.

        Keyed human attestation

        Obligations and relationships become load-bearing only when a registered signer attests them with an Ed25519 receipt. Proposed items stay visibly proposed until then.

        Deploy where the data lives

        Dedicated cloud control plane, your VPC, or fully on-premises. Journals stay in your custody; verification runs anywhere the digest does.

        Interaction records

        Every consequential model action, refusals included, is written as metadata to the journal. Governance that records what the system decided but not what the model did has a hole in the middle.

        Signer registry

        Bring your own key registry. Rotate signers, revoke receipts, and keep a chain of custody from the person who attested to the projection that relied on it.
